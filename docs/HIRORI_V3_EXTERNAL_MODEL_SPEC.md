# ヒロリV3 外部制作モデル 受け入れ仕様

TOMORI のキャラクター「ヒロリ」の3Dモデルを、外部のサービスや3D制作者に作ってもらうときの条件をまとめた。
この文書は、依頼の前に相手へ渡す。届いたモデルは `tools/validate-hirori-v3.mjs` で検査してから受け入れる。

この時点では、どのサービスにも画像やファイルを送っていない。ゲームのコードにも新しいモデルは入れていない。

## 1. キャラクターの条件

正式な見た目は、4枚の設定画像（正式基準・回転図・部分図・動き）で決まっている。資料のあいだで食い違うときは、正式基準（全身1体の画像）を優先する。

### 色

- 3色が中心：珊瑚色（体の外側）、クリーム色（顔・のど・胸・おなか）、淡い水色（羽の内側・とさかの内側）
- 珊瑚色は、赤すぎず、ピンクへ寄せすぎない温かい色
- クリーム色は、真っ白にしない
- 水色は、紫や灰色へ寄せない

### 形

- 鼻はない
- 尻尾はない
- 前脚にあたる部分は、左右2枚の羽。羽は一枚の柔らかな翼で、羽根を何枚も並べない。指・爪はない
- 足は丸い3本指。爪・水かきもない
- 首は頬から細くなって胸へ広がる、軽いS字の形（太さが一定の円筒にしない）
- ペンギン・フクロウ・鳥の着ぐるみに見せない。柔らかいが軽やかな、小さな生き物

### とさか（最も大切な特徴）

- 4枚。頭のまんなかの線の上を、顔側から後頭部へ一直線に並ぶ（左右に対で置かない）
- 先頭（顔側）の1枚が最も大きく、うしろへ順に小さくなる
- 1枚ずつは、ふっくらした細長い花びら。根元は細く、途中が最も広く、先は丸い
- 横から見ると、上・うしろへ流れる4枚が重ならずに読める
- 花のように放射状に広げない。耳・角・王冠・たてがみに見せない
- 後頭部は、とさか以外のこぶやふくらみのない、なめらかな卵形

### 背面・真上

- 背面から、目・顔・クリーム色が見えない
- 真上から見て、顔側と後頭部側が正しい（とさかは前が大きい）

## 2. GLB の条件

| 項目 | 条件 |
|---|---|
| 形式 | glTF 2.0 のバイナリ（GLB）。1ファイルで完結する |
| 外部ファイル | 外部 URI なし（別の .bin・画像ファイルを参照しない） |
| テクスチャ | 使う場合は GLB の中に埋め込む |
| 初回の候補 | 静止モデルでよい（アニメーション・リグなしで可） |
| 大きさ | 全高 約1.0（とさかの先まで）。0.9〜1.1 |
| 足裏 | Y = 0（地面の高さ） |
| 左右の中心 | X = 0 |
| 上方向 | +Y |
| 前方向 | +Z（glTF の標準。Three.js にそのまま読み込むと、カメラの側を向く） |
| 三角形 | 25,000 以下を目標。40,000 が上限 |
| ファイルの大きさ | 3MB 以下を目標。8MB が上限 |
| マテリアル | 8 以下 |
| 入れないもの | カメラ・ライト・床・背景の板 |
| 名前 | 個人名・PC の絶対パス（`C:\Users\…` など）をファイルの中に残さない |

## 3. あとでリギングするための部位

骨やアニメーションは、受け入れたあとに TOMORI 側で入れる。そのために、次の部位を別のオブジェクト（ノード）に分けておく。

| 部位 | ノード名の例 |
|---|---|
| 全体の親 | `Root` |
| 胴 | `Body` |
| 頭 | `Head` |
| 羽 | `Wing_L` / `Wing_R` |
| 脚 | `Leg_L` / `Leg_R` |
| 足 | `Foot_L` / `Foot_R` |
| とさか | `Crest_01`（顔側・最大）〜 `Crest_04`（後頭部側・最小） |
| 目 | `Eye_L` / `Eye_R` |

名前が完全に同じである必要はない。違う名前のときは、どのノードがどの部位かの対応表（manifest）を一緒に受け取る。
頭と胴が1つのメッシュでもよいが、そのときは首・肩・股・足首・とさかの根元が曲げやすい形（関節のまわりに頂点の輪がある）にしてもらう。

## 4. 受け入れの手順

1. 届いた GLB を、リポジトリの外のフォルダに置く（リポジトリへは、検査に合格して採用が決まるまで入れない）
2. 検査ツールを実行する

   ```
   node tools/validate-hirori-v3.mjs <ファイル.glb>
   ```

   - 「不合格」が1つでもあれば受け入れない
   - 「注意」は、内容を見て判断する（部位の名前が足りない場合は、対応表があればよい）
   - ツールはファイルを読むだけで、書きかえない。通信もしない
3. Blender で正面・横・背面・斜め・真上を撮り、設定画像と並べて見た目を確かめる（1章の条件）
4. 合格したら、SHA-256 と検査の結果を記録して、HQ が採用を決める

### 検査ツールが確かめること

- 形式：ファイルの有無、先頭の `glTF`、version 2、ファイルの大きさ、外部 URI
- 数：メッシュ・ノード・マテリアル・テクスチャ・画像・アニメーション・スキン・カメラ・ライト・三角形
- 大きさ：バウンディングボックス・全高・足裏の高さ・左右の中心
- 名前：禁止の部位らしい名前（尻尾・腕・手・指・爪・耳・角・鼻）、要らないノード（カメラ・床など）、部位の名前
- その他：個人のパスらしい文字列、SHA-256

## 5. 人が確かめること（検査ツールの合否に含まれない）

- サービスの利用規約で、作ったモデルを TOMORI（教育用のアプリ・テレビ収録・コンテスト応募）で使えるか
- 生成物の権利（著作権・商用利用・クレジットの表記）が、だれにあるか
- 設定画像をアップロードしてよいサービスか（画像が学習に使われないか、公開されないか）
- 有料の契約が必要か（契約は HQ の判断のあとにする）
- 届いたモデルが、他の作品のキャラクターに似すぎていないか
